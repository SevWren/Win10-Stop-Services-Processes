## ADR-0005 — Graceful-Only Service Stop; No Force-Kill Fallback

### Check 1: No `TerminateProcess` call in `ServiceManager.au3`

**Result: PASS**

A repo-wide grep for `TerminateProcess` returns zero matches in `Includes/ServiceManager.au3`. The only occurrences of that string in the repo are in documentation files (`docs/domain-modeling/proposals/DM-03-stop-terminate-semantics.md`, `docs/domain-modeling/DOMAIN-MODEL.md`, etc.) and a comment in `Stop Services Processes.au3` line 203 that describes the process-kill path (`_CloseInstaller`), not any service-stop path. No `TerminateProcess` call exists, directly or via wrapper, inside `ServiceManager.au3`.

### Check 2: TIMED_OUT branch closes handles without killing the process

**Result: PASS**

Lines 364–372 of `ServiceManager.au3` handle the timeout case. After the Phase 2 `WEnd` exits (deadline exceeded), the remaining entries in `$aPendingIdx` are iterated:

- `$aResults[$iTOIdx][3]` is set to `$SM_OUTCOME_TIMEDOUT` ("TIMED_OUT")
- `$aResults[$iTOIdx][5]` is set to `"Deadline exceeded (<N>ms)"`
- `DllCall("advapi32.dll", "bool", "CloseServiceHandle", "handle", $aPendingHnd[$iTimeoutIdx])` closes the per-service handle

No Win32 process-termination call (`TerminateProcess`, `ProcessClose`, or any equivalent) appears in this branch or anywhere in the function. The service host process is left running exactly as the ADR specifies.

### Check 3: TIMED_OUT retry cadence — accuracy of the "10 s tick" claim

**Result: PASS — claim is accurate**

ADR-0005 Context section states: "The monitoring loop retries on the next `$SVC_POLL_INTERVAL_SEC` (10 s) tick."

Confirmed in `Stop Services Processes.au3`:

- Line 43: `Global Const $SVC_POLL_INTERVAL_SEC = 10`
- Line 171: `If _CheckElapsedTime($iLastStopServices, $SVC_POLL_INTERVAL_SEC) Then`

The monitoring loop calls `_stopservicescustom` (which will invoke `_SM_StopServicesBatch`) once every 10 seconds. The 10 s figure in the ADR is accurate.

Note: CLAUDE.md's architecture section states the monitoring loop calls both `_CloseInstaller` and `_stopservicescustom` "every ~2 seconds." This is imprecise — CLAUDE.md describes them together at the wrong granularity. The actual intervals are `$PROC_POLL_INTERVAL_SEC = 2` for process kills and `$SVC_POLL_INTERVAL_SEC = 10` for service stops. ADR-0005 is correct; CLAUDE.md is misleading on this point but that is outside the scope of this ADR review.

### ADR-0005 format compliance (ADR-FORMAT.md)

The ADR follows the format. It carries a `Status: Accepted` frontmatter line, a `Considered options` section (rejected alternative documented with reasoning), and a `Consequences` section (positive and negative effects). All three optional sections are justified: the rejection of `TerminateProcess` is a non-obvious trade-off that future readers would question, and the negative consequence (a protected service that never stops) is a real ongoing limitation. Compliant.

## ADR-0006 — SCM Handle Opened Once Per Batch Stop Cycle

### Check 1: `OpenSCManagerW` appears exactly once in `_SM_StopServicesBatch`

**Result: PASS**

Grep over `ServiceManager.au3` for `OpenSCManagerW` returns two lines:

- Line 170: the actual `DllCall(... "OpenSCManagerW" ...)` — the single real call
- Line 177: a log-message string literal `"OpenSCManagerW failed ..."` — not a call

There is exactly one `OpenSCManagerW` invocation in `_SM_StopServicesBatch` (and in the entire file). No other function in `ServiceManager.au3` opens an SCM handle.

### Check 2: `CloseServiceHandle($hSCM)` appears exactly once, after Phase 2

**Result: PASS**

All `CloseServiceHandle` calls in `ServiceManager.au3` with line numbers:

| Line | Argument | Context |
|------|----------|---------|
| 237 | `$hService` | Phase 1 — QueryServiceStatus failure, early-out |
| 250 | `$hService` | Phase 1 — already stopped, early-out |
| 271 | `$hService` | Phase 1 — START_PENDING (un-stoppable), early-out |
| 297 | `$hService` | Phase 1 — ControlService failure, early-out |
| 343 | `$hPendSvc` | Phase 2 — service reached STOPPED, removed from pending list |
| 371 | `$aPendingHnd[$iTimeoutIdx]` | Timeout sweep — per-service handle close |
| **376** | **`$hSCM`** | **Batch-level SCM handle close — after timeout sweep** |

`$hSCM` is closed exactly once, at line 376, which is after the Phase 2 poll loop and the timeout handle-close sweep. This matches the ADR's stated invariant: "$hSCM is closed only after all per-service handles and the Phase 2 poll loop are complete."

### Check 3: `ServiceControl.au3` functions each open/close SCM independently

**Result: PASS — with one omission noted**

`ServiceControl.au3` defines six functions:

| Function | Line | Opens SCM | Closes SCM |
|----------|------|-----------|------------|
| `_StartService` | 97 | Line 109 (`OpenSCManager`) | Line 137 (`CloseServiceHandle $hSC`) |
| `_StopService` | 157 | Line 169 (`OpenSCManager`) | Line 197 (`CloseServiceHandle $hSC`) |
| `_ServiceExists` | 216 | Line 224 (`OpenSCManager`) | Line 238 (`CloseServiceHandle $hSC`) |
| `_ServiceRunning` | 255 | Line 264 (`OpenSCManager`) | Line 283 (`CloseServiceHandle $hSC`) |
| `_CreateService` | 314 | Line 335 (`OpenSCManager`) | Line 372 (`CloseServiceHandle $hSC`) |
| `_DeleteService` | 391 | Line 403 (`OpenSCManager`) | Line 429 (`CloseServiceHandle $hSC`) |

Every function opens its own SCM handle at entry and closes it before returning. This confirms the per-call pattern described in the ADR.

**Minor inaccuracy in ADR-0006:** The ADR's opening paragraph lists "every function (`_StopService`, `_StartService`, `_ServiceExists`, `_ServiceRunning`, `_DeleteService`)" — five functions. It omits `_CreateService`. `_CreateService` is present in `ServiceControl.au3` (line 314) and follows the same per-call SCM pattern. The omission does not invalidate the architectural claim, but the function list is incomplete.

**Severity: Minor / Informational.** The ADR's design claim (each function is self-contained) is correct. The list just needs `_CreateService` added.

### ADR-0006 format compliance (ADR-FORMAT.md)

The ADR omits a `Status` line and a document title header in the conventional `# Short title` form — the first line is used as the title inline with the opening paragraph, which is acceptable under the format's minimal template. The `Considered Options` section documents the rejected per-call pattern and the rationale for the batch-scoped choice, which is exactly the non-obvious trade-off the format targets. The `Consequences` section correctly flags the stale-handle risk and the convention-only boundary enforcement. Compliant.

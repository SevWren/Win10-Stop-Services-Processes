## ADR-0007 — AutoIt Priority Constants as Canonical Internal Representation

### Checklist Results

**1. Are `$AUTOIT_PRIORITY_*` constants (0–5) defined in `Stop Services Processes.au3`?**

PASS. Lines 72–77 of `Stop Services Processes.au3` define all six constants inside a dedicated `#Region ;Configuration — AutoIt process priority constants` block:

```autoit
Global Const $AUTOIT_PRIORITY_IDLE         = 0
Global Const $AUTOIT_PRIORITY_BELOW_NORMAL = 1
Global Const $AUTOIT_PRIORITY_NORMAL       = 2
Global Const $AUTOIT_PRIORITY_ABOVE_NORMAL = 3
Global Const $AUTOIT_PRIORITY_HIGH         = 4
Global Const $AUTOIT_PRIORITY_REALTIME     = 5
```

The region comment explicitly states these are AutoIt-layer constants distinct from Windows API hex values, and cross-references `_WinAPIPriorityClassToAutoItConst()`. This directly fulfils the ADR-0007 mandate.

**2. Are `$AUTOIT_PRIORITY_*` constants used at ALL `ProcessSetPriority` call sites?**

PASS. There are three `ProcessSetPriority` call sites in the file:

- Line 352 (`SetProcessPriority` function): `ProcessSetPriority($iPID, $iPriorityConst)` where `$iPriorityConst` is assigned from a `Switch` on `$sPriorityLevel` that sets it to `$AUTOIT_PRIORITY_BELOW_NORMAL`, `$AUTOIT_PRIORITY_NORMAL`, or `$AUTOIT_PRIORITY_ABOVE_NORMAL` — lines 320, 322, 324.
- Line 444 (`LockProcessPriority` function): `ProcessSetPriority($iPID, $iPriorityConst)` where `$iPriorityConst` is range-validated against `$AUTOIT_PRIORITY_IDLE` and `$AUTOIT_PRIORITY_REALTIME` (line 429), and the user-supplied integer was cast from a string — not from a raw hex value.
- Line 503 (`_PriorityWatchdog` function): `ProcessSetPriority($iPID, $iPriorityConst)` where `$iPriorityConst` is read directly from `$aPriorityWatchTargets[$i]` — the watchdog parallel array.

No call site passes a raw hex literal. All paths trace to the named constants or to values stored via those constants. Full compliance.

**3. Does `_GetProcessPriorityByPID` call `_WinAPIPriorityClassToAutoItConst` before comparison? (The mandatory conversion bridge)**

PASS. The function at lines 530–551 ends with:

```autoit
Return _WinAPIPriorityClassToAutoItConst($aResult[0])
```

This is the sole return path for a successful read. The raw `GetPriorityClass` DWORD (`$aResult[0]`) is never stored, compared, or logged before being passed through the bridge. The return value of `_GetProcessPriorityByPID` is an AutoIt integer (0–5) or -1 on error.

The comparison at line 489 (`If $iCurrentConst <> $iPriorityConst Then`) therefore compares two AutoIt integers — the converted current value against the stored target from `$aPriorityWatchTargets`. This is exactly what ADR-0007 mandates.

`_WinAPIPriorityClassToAutoItConst` itself (lines 558–575) is a pure Switch on the six WinAPI hex values (`$IDLE_PRIORITY_CLASS` etc.) returning the corresponding AutoIt integer, with a `-1` sentinel for unrecognised values. The implementation matches the ADR description precisely.

**4. Is `$aPriorityWatchTargets[]` storing AutoIt integers (0–5), not hex values?**

PASS. The array is declared at line 117:

```autoit
Global $aPriorityWatchTargets[0]   ; corresponding target AutoIt priority constants (0–5)
```

Values are written to it in exactly one place: `LockProcessPriority` at line 453:

```autoit
_ArrayAdd($aPriorityWatchTargets, $iPriorityConst)
```

`$iPriorityConst` at that point is an integer cast from user input (`Int($sRawPriority)`, line 428), range-validated against `$AUTOIT_PRIORITY_IDLE` (0) and `$AUTOIT_PRIORITY_REALTIME` (5). It is never sourced from a `GetPriorityClass` call or any Windows API hex value. The array can only ever contain integers in the range 0–5. Full compliance.

### ADR-0007 Prose Assessment

The ADR has a title, an Options section (Option A chosen / Option B rejected), and a Consequences section. It has no explicit "Status" field (e.g., Accepted/Superseded). The absence of ADR-FORMAT.md makes it impossible to call this a format violation, but it is worth noting for consistency if that file is later created. No factual errors found in the prose — the rationale accurately describes the implementation.

### ADR-0007 Verdict: PASS — All four checklist items confirmed.

## ADR-0008 — Direct DllCall to advapi32.dll for SCM Operations

### Checklist Results

**1. Does `ServiceManager.au3` use direct `DllCall("advapi32.dll", ...)` exclusively (not AutoIt built-in service wrappers)?**

PASS. Every SCM operation in `ServiceManager.au3` uses `DllCall("advapi32.dll", ...)`. The specific calls and their locations:

| Call | Location |
|---|---|
| `OpenSCManagerW` | Line 170 — batch-level SCM open |
| `OpenServiceW` | Line 203 — per-service open (Phase 1) |
| `QueryServiceStatus` (Phase 1) | Line 228 — initial state read |
| `ControlService` | Line 279 — stop control |
| `CloseServiceHandle` (service, success path) | Lines 237, 250, 271, 297, 343 |
| `CloseServiceHandle` (service, timeout path) | Line 371 |
| `CloseServiceHandle` (SCM) | Line 376 |
| `QueryServiceStatus` (Phase 2 poll) | Line 325 |
| `QueryServiceStatus` (_SM_GetServiceState) | Line 399 |

There is no call to `ServiceStop()`, `_ServiceStop()`, `_Service_Stop()`, `_WinAPI_*`, or any other AutoIt built-in service wrapper anywhere in the file. The `#include-once` directive at the top imports nothing external except what is inherited at the main-script level. Compliance is complete.

The capture-immediately pattern required by ADR-0008's Consequences section is also observed throughout: `Local $iXxxDllErr = @error` appears on the line directly after every `DllCall`, followed by `Local $iXxxWinErr = _WinAPI_GetLastError()` before any subsequent call. Spot-checks:

- Lines 174/176 (OpenSCManagerW)
- Lines 207/209 (OpenServiceW)
- Lines 231/232 (QueryServiceStatus Phase 1)
- Lines 283/284 (ControlService)
- Lines 328/330 (QueryServiceStatus Phase 2 poll — DllErr captured line 328; note WinErr not captured on poll-query fail path at line 329, only DllErr is used to gate the defer. This is a minor deviation from the stated pattern but not a logic error since the poll-failure path only logs and continues.)

**2. Cross-reference with CLAUDE.md: is the same rationale documented for kernel32.dll?**

PASS with one observation.

ADR-0008 explicitly references the kernel32.dll rationale in its "AutoIt `_WinAPI_*` wrappers (rejected)" section:

> `CLAUDE.md` documents this for `_WinAPI_GetPriorityClass` on the kernel32.dll path; the same reliability concern applies to any `_WinAPI_*` wrapper over advapi32.dll.

`CLAUDE.md` confirms this in the AutoIt Version Compatibility Notes table:

> `_WinAPI_GetPriorityClass` wrapper propagates unreliable `@error` values → `_GetProcessPriorityByPID` uses direct `DllCall("kernel32.dll", ...)` instead

And in the WinAPI Priority Reading Pattern section:

> The correct pattern for reading a process priority class — do not use `_WinAPI_GetPriorityClass`

The cross-reference is accurate and bidirectional. ADR-0008 cites CLAUDE.md as evidence; CLAUDE.md independently records the same decision. The two documents are consistent.

**Observation:** ADR-0008 also references ADR-0001 ("gaps with protected services ... Rejected for the same reasons recorded in ADR-0001"). ADR-0001 was not part of this review scope, but it is referenced twice in ADR-0008 and should be verified in a separate pass if not already reviewed.

### ADR-0008 Prose Assessment

The ADR has a title, three options (Direct DllCall chosen, two variants rejected), and a Consequences section. As with ADR-0007, there is no Status field. The Consequences section lists four concrete obligations (capture pattern, type signatures, portability, do-not-introduce-wrappers) all of which are observable in the implementation. No factual errors in the prose.

**Minor observation — Phase 2 poll WinErr capture:** The Consequences section states: "Local $iDllErr = @error on the line directly after DllCall, then Local $iWinErr = _WinAPI_GetLastError() before any other call." The Phase 2 poll-query failure path (lines 329–332 of ServiceManager.au3) captures `$iPollDllErr = @error` but does not separately capture `_WinAPI_GetLastError()`. Since this branch only defers (logs and ContinueLoops without classifying a Win32 error), the omission has no functional impact. However, it is a minor deviation from the stated pattern that could confuse a future maintainer adding error classification to that path.

### ADR-0008 Verdict: PASS — Direct DllCall usage confirmed throughout; CLAUDE.md cross-reference is accurate. One minor pattern deviation noted (Phase 2 poll-fail path, no WinErr capture), no functional consequence.

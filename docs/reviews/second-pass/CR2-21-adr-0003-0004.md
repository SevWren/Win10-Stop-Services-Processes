## ADR 0003 — Two-level error reporting in `_SM_StopServicesBatch`

### Claim 1: `@error=1` is set ONLY for SCM open failure

**Verdict: CONFIRMED — accurate.**

The only `SetError(1)` call in the entire function is at lines 181–182, inside the branch that fires when `OpenSCManagerW` returns a null handle or `DllCall` itself fails:

```autoit
If $iScmDllErr Or Not $aScmOpen[0] Then
    ...
    SetError(1)
    Return $aEmpty
EndIf
```

No other path in the function calls `SetError`. The function ends with a plain `Return $aResults` (line 378), which leaves `@error` at its AutoIt default of 0. Every other failure mode — including every per-service failure path — uses `ContinueLoop` after writing directly into `$aResults[$i][3]` and `$aResults[$i][4]`, never touching `@error`.

### Claim 2: Per-service failures (FAILED, TIMED_OUT) return with `@error=0`

**Verdict: CONFIRMED — accurate.**

Tracing every failure branch in Phases 1 and 2:

| Failure scenario | Outcome written | `@error` modified? |
|---|---|---|
| `OpenServiceW` fails (not found) | `$SM_OUTCOME_UNAVAILABLE` → `[i][3]` | No — `ContinueLoop` |
| `OpenServiceW` fails (other Win32) | `$SM_OUTCOME_FAILED` → `[i][3]` | No — `ContinueLoop` |
| `QueryServiceStatus` fails (Phase 1) | `$SM_OUTCOME_FAILED` → `[i][3]` | No — `ContinueLoop` |
| State is START_PENDING (not stop-eligible) | `$SM_OUTCOME_FAILED` → `[i][3]` | No — `ContinueLoop` |
| `ControlService` fails | `_SM_Win32ErrToOutcome()` → `[i][3]` | No — `ContinueLoop` |
| Timeout expiry (Phase 2) | `$SM_OUTCOME_TIMEDOUT` → `[i][3]` | No — plain loop |

The timeout loop (lines 365–372) iterates `$aPendingIdx` and writes `$SM_OUTCOME_TIMEDOUT` into the result array rows. It does not call `SetError`. The function then falls through to `Return $aResults` at line 378 — `@error` remains 0.

### Claim 3: The silent-success hazard is real

**Verdict: CONFIRMED — genuine and non-trivial.**

The hazard is real for the following reason: `_SM_StopServicesBatch` returns `@error=0` after a batch in which every single service timed out or failed. A caller written as:

```autoit
Local $aResult = _SM_StopServicesBatch($aNames)
If @error Then
    ; handle batch failure
Else
    ; assumes all stopped
EndIf
```

...will silently enter the `Else` branch even when no service stopped at all. The ADR correctly identifies this as the consequence of the two-level design and states the mitigation: "callers must iterate the returned array and inspect each row's outcome string."

The hazard is not a defect in the implementation — it is the designed trade-off — but it is a genuine API footgun and ADR 0003's warning about it is both accurate and necessary.

**One precision note (non-blocking):** ADR 0003 mentions "FAILED rows" in its consequence paragraph. The full set of outcomes a caller must check for is FAILED, TIMED_OUT, and UNAVAILABLE — not just FAILED. The ADR's body implies this but does not enumerate all three outcome strings explicitly. The code uses `$SM_OUTCOME_FAILED`, `$SM_OUTCOME_TIMEDOUT`, and `$SM_OUTCOME_UNAVAILABLE`. The ADR's consequence statement would be more precise if it said "FAILED, TIMED_OUT, or UNAVAILABLE rows."

**ADR 0003 overall: ACCURATE. No corrections required.**

## ADR 0004 — `ServiceManager.au3` deliberately uses a different error convention than `ServiceControl.au3`

### Claim 1: `ServiceControl.au3` functions return `1`/`0` with Win32 `@error`

**Verdict: CONFIRMED — accurate.**

Inspecting `_StopService`, `_StartService`, `_CreateService`, and `_DeleteService` in `ServiceControl.au3`:

- All four functions initialise `$lError = -1` and use the pattern: if any DllCall fails, call `GetLastError` and assign the Win32 code to `$lError`.
- At function exit, the pattern is:
  ```autoit
  If $lError <> -1 Then
      SetError($lError)
      Return 0
  EndIf
  Return 1
  ```
- `_ServiceExists` and `_ServiceRunning` are simpler (no `@error` path — they return `1`/`0` directly from success/failure of the DllCall chain), which is consistent with their documented contract (no `@error` noted in their headers).

The `1`/`0` / Win32-`@error` pattern described in ADR 0004 is exactly what the code implements for the mutating functions (`_StopService`, `_StartService`, `_CreateService`, `_DeleteService`).

### Claim 2: `_SM_StopServicesBatch` returns a 2D array with `@error` = batch-level only

**Verdict: CONFIRMED — accurate.** (This is the same finding as ADR 0003 Claim 1 and 2 above, confirmed from the same source trace.)

The function returns a `[n][6]` array and sets `@error` to 1 only on SCM-open failure. All per-service outcomes are encoded in column `[i][3]` of the array.

### Claim 3: The incompatibility is genuine and permanent

**Verdict: CONFIRMED — accurate, and the reasoning is sound.**

The ADR states the incompatibility is structural: `_StopService` sends a stop control and returns before the service has actually stopped; it cannot return per-service state transitions. This is verified by the `_StopService` source code, which:

1. Issues `ControlService` with `SERVICE_CONTROL_STOP`.
2. Checks only whether the DllCall return value is zero.
3. Does not query state after sending the stop control.
4. Does not poll.
5. Its own comment header reads: "This function does not check to see if the service has stopped successfully."

There is no mechanism in `_StopService` to produce the structured outcome data (`STOPPED`, `TIMED_OUT`, `ALREADY_STOPPED`) that `_SM_StopServicesBatch` is built to provide. Conforming `_SM_StopServicesBatch` to the scalar `1`/`0`/`@error` convention would require discarding the per-service state-machine and polling loop entirely — which would eliminate the module's reason for existence.

The ADR's conclusion that the split "is permanent as long as both modules coexist" is therefore correct.

**One additional observation (informational, non-blocking):** ADR 0004 describes `ServiceControl.au3`'s functions as setting `@error` to "Win32 error code directly." This is accurate for `_StopService` and the other mutating functions. However, `_ServiceRunning` does not follow this convention — it returns `1`/`0` based on whether `ControlService` with `SERVICE_CONTROL_INTERROGATE` succeeds, and does not call `GetLastError` or set `@error` at all. This is not an error in the ADR — `_ServiceRunning` is not a stop function and the ADR only claims the convention for stop operations — but a reviewer maintaining either file should be aware that `_ServiceRunning`'s `@error` behaviour differs from the other functions in `ServiceControl.au3`.

**ADR 0004 overall: ACCURATE. No corrections required.**

Two precision notes are recorded above (ADR 0003: enumerate all three non-success outcome strings in the consequence statement; ADR 0004: `_ServiceRunning` does not set `@error`, unlike the mutating functions), but neither rises to the level of an inaccuracy in the ADR's stated claims.

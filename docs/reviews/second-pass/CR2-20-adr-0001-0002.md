## Standards — ADR-FORMAT.md compliance

### ADR 0001

**Title:** Passes. Concise and descriptive.

**Opening paragraph:** Passes. Covers context (the old `_StopService` path's deficiencies), the decision (extract into `ServiceManager.au3` as a deep module with one public function), and the rationale (batch algorithm, structured outcomes, shared deadline). Three sentences, well within the 1–3 sentence guideline.

**Considered Options section:** Warranted and correctly used. All three alternatives (patch `_StopService`, call AutoIt's built-in `ServiceStop()`, the chosen batch module) involve real trade-offs with non-obvious rejection reasons. This qualifies under ADR-FORMAT.md's "Rejected alternatives when the rejection is non-obvious."

**Consequences section:** Warranted and correctly used. It calls out two non-obvious downstream effects: (a) the call site in the main monitoring loop becomes more verbose, and (b) the convention-only boundary between `ServiceControl.au3` and `ServiceManager.au3` is not enforced by an interface. Both are non-obvious to a future reader. The format spec explicitly endorses this section "only when non-obvious downstream effects need to be called out."

**No boilerplate headers present.** Status frontmatter is absent; the decision reads as accepted by default and there is no active controversy, so omitting it is correct.

**Verdict: Compliant.**

### ADR 0002

**Title:** Passes. Concise, specific, and self-contained.

**Opening paragraph:** Passes. Names the function (`_SM_IsStopEligible()`), names the state (`START_PENDING`), names the outcome (`FAILED` with Win32 error 1061), and gives the rationale (non-deterministic timing, untestable without real SCM, 10-second retry cycle makes the extra delay acceptable). This is denser than 1–3 sentences but all content is load-bearing context for the decision. No padding.

**Considered Options section:** Warranted. The three options (attempt and handle, treat as polling candidate, mark FAILED immediately) are genuinely distinct approaches with non-obvious rejection reasons. The rejection of "Treat as Pending" is especially worth recording — a reader familiar with Phase 2 polling would naturally wonder why START_PENDING isn't routed there.

**Consequences section:** Warranted. The worst-case extra delay (`$SVC_POLL_INTERVAL_SEC`, 10 seconds) and the specific variable name are non-obvious without reading the code. Calling this out explicitly meets the bar.

**No boilerplate headers present.** Correct.

**Verdict: Compliant.**

## Spec — Decisions verified against `Includes/ServiceManager.au3`

### ADR 0001, Claim 1: "single public function: `_SM_StopServicesBatch`"

The file header comment (lines 13–26) explicitly partitions the interface:

```
; PUBLIC INTERFACE
;   _SM_StopServicesBatch(ByRef $aServiceNames [, ...])
;
; INTERNAL HELPERS (not called from main script)
;   _SM_GetServiceState, _SM_ServiceStateToString, _SM_Win32ErrToOutcome,
;   _SM_IsStopEligible, _SM_StateNeedsPolling, _SM_StateToAlreadyStopped,
;   _SM_BuildResultRow
```

Counting defined `Func` blocks: `_SM_StopServicesBatch`, `_SM_GetServiceState`, `_SM_ServiceStateToString`, `_SM_Win32ErrToOutcome`, `_SM_IsStopEligible`, `_SM_StateNeedsPolling`, `_SM_StateToAlreadyStopped`, `_SM_BuildResultRow` — **8 functions total, 1 public**.

The ADR's claim of one public function is accurate. Note that AutoIt has no access-modifier syntax, so the boundary is enforced only by the header comment and naming convention, exactly as the ADR states.

**Verdict: Accurate.**

### ADR 0001, Claim 2: Convention-only boundary (not enforced)

ADR 0001 Consequences, paragraph 2:

> "This boundary is not enforced by an interface — it is a naming and inclusion convention."

The code confirms this. AutoIt `#include-once` provides no encapsulation; all `Func` blocks in `ServiceManager.au3` are callable by any script that includes the file. The "internal helpers" designation exists only in comments and in the `_SM_` prefix convention. The ADR documents this correctly.

**Verdict: Accurately documented.**

### ADR 0002, Claim 1: `_SM_IsStopEligible` returns False for `START_PENDING`

`_SM_IsStopEligible` is at lines 476–483:

```autoit
Func _SM_IsStopEligible($iState)
    Switch $iState
        Case $SM_STATE_RUNNING, $SM_STATE_PAUSED, $SM_STATE_PAUSE_PENDING, $SM_STATE_CONTINUE_PENDING
            Return True
        Case Else
            Return False
    EndSwitch
EndFunc
```

`$SM_STATE_START_PENDING = 2` (line 45). It is not listed in the `Case` branch, so the function returns `False` for it. This is correct and matches the ADR's claim.

**Verdict: Accurate.**

---

### ADR 0002, Claim 2: START_PENDING is routed to FAILED (not UNAVAILABLE or TIMED_OUT)

The routing logic in `_SM_StopServicesBatch` Phase 1 (lines 264–273):

```autoit
If Not _SM_IsStopEligible($iInitState) Then
    ; START_PENDING: cannot receive stop control now — mark FAILED
    $aResults[$i][2] = $iInitState
    $aResults[$i][3] = $SM_OUTCOME_FAILED
    $aResults[$i][4] = $SM_ERR_CANNOT_ACCEPT
    $aResults[$i][5] = "Service in START_PENDING state; stop control not accepted"
    ...
    ContinueLoop
EndIf
```

`$SM_OUTCOME_FAILED = "FAILED"` (line 58). `$SM_ERR_CANNOT_ACCEPT = 1061` (line 67), which is `ERROR_SERVICE_CANNOT_ACCEPT_CTRL`. The ADR states "outcome `FAILED` (Win32 error 1061)" — both the outcome string and the error code are correct.

The service does not reach the `_SM_StateNeedsPolling` branch (which routes to Phase 2 polling) or any path that assigns `UNAVAILABLE` or `TIMED_OUT`. The `ContinueLoop` exits Phase 1 immediately after setting `FAILED`.

**Verdict: Accurate.**
